So yeah I think that this is a good thing to push back on, namely I have seen LLM powered rewrites from go -> rust go pretty well (Also importantly the existing binary hasn't been deployed yet and has had exactly zero bugtesting, and in my opinion its absolutely worth it to have a single language for the entire project so any language move would incur a rewrite). As for memory safety there aren't really any benefits for rust over golang since both have a garbage collector. There also aren't any performance or binary size problems we need to worry about, namely because the homelab is running .NET and python web applications, so the performance considerations of the forwarder and dashboard are mostly irrelavent. The main thing I care about is desigining for a process where we encounter the fewest amount of bugs, and can guarentee as many things ahead of time work. There is an argument that Golang helps with discovering bugs because the code is simpler to reason about, compared to rusts tradeoff regarding the compiler eliminating certain classes of bugs. (more discussion here: https://fasterthanli.me/articles/i-want-off-mr-golangs-wild-ride). There is also a secondary question in this application, namely does even moving to a language like rust even help in an application like this where most of the bad behavior comes from source bugs in other buggy external systems?
